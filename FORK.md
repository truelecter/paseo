# Fork: `truelecter/paseo`, branch `local`

`local` is an upstream release tag (betas included) plus a few commits of our own and squashes of open upstream pull requests. When a new tag sits on a release branch and lacks upstream `main` fixes the previous base already had, `local` also carries cherry-picks of those fixes, so moving to the tag takes nothing away. Each change of our own also lives on its own branch, based on upstream `main` so it can become a pull request; `local` carries a cherry-pick of it. An upstream pull request is carried as one squash of its diff against its merge base with `main`. This file lists everything on `local` that upstream doesn't have, and when each piece can go.

## Android APK

`.github/workflows/android-tlctr-apk.yml` needs three repository secrets: `PASEO_GOOGLE_SERVICES_JSON` (the Firebase `google-services.json` for `sh.paseo.tlctr`, base64), `PASEO_ANDROID_KEYSTORE` (the release keystore, base64, key alias `paseo`), and `PASEO_ANDROID_KEYSTORE_PASSWORD`. The Expo project `@trlctr/paseo` holds the FCM V1 service account key for `sh.paseo.tlctr`; the daemon sends pushes through Expo with the token the app registers, so the daemon needs nothing extra. Keep the keystore: an APK signed with another key can't update the installed app.

The version comes from upstream (`packages/app/package.json`), so it moves when `local` moves to a newer tag. Each build of one version gets a build number from the workflow (`PASEO_TLCTR_BUILD`, one more than the highest `<version>-tlctr.<n>` release, at most 99): versionName `<version>-tlctr.<n>`, the same as the release tag, and versionCode `<upstream versionCode> * 100 + <n>`. The app's own version checks read `package.json`, so the suffix doesn't change them. Local builds without the variable are build 0.

To build locally: `APP_VARIANT=tlctr GOOGLE_SERVICES_FILE_TLCTR=<file> npx expo prebuild --platform android --clean` in `packages/app`, then `PASEO_ANDROID_KEYSTORE_FILE=<jks> PASEO_ANDROID_KEYSTORE_PASSWORD=<password> ./gradlew :app:assembleRelease -PreactNativeArchitectures=arm64-v8a` in `packages/app/android`. Without the keystore variables the release APK is signed with the debug key.

## Move to a newer upstream

1. Take the newest release tag, betas included (`^v[0-9]+\.[0-9]+\.[0-9]+(-beta\.[0-9]+)?$`, newest by tag date). Nothing to do when it is already an ancestor of `local`.
2. If the new tag doesn't contain the commit named in "Base" (upstream cuts some patch releases on a release branch off an older tag), list what the old base had that the tag lacks: `git cherry -v <new tag> <old base>`. Each `+` line except `fix: update lockfile signatures and Nix hash` gets cherry-picked with `-x` right on top of the tag and a row in the table, so moving to the tag takes no fix away. Backports already in `local` come along as ordinary carried commits, and the rebase drops them once a tag contains them.
3. Rebase: `git rebase -i --onto <new tag> <old base> local`, with one `exec git cherry-pick -x <sha>` line per new backport at the top of the todo list. Commits upstream already has drop out.
4. Resolve conflicts instead of aborting:
   - `nix/npm-deps.hash`: take the tag's side, the npm deps hash check below sets it.
   - `package-lock.json`: keep the tag's file and redo the carried commit's own entries on it (`git show <commit> -- package-lock.json`).
   - `patches/*.patch` (patch-package): don't merge patch text. Unpack the package versions involved (`npm pack <name>@<version>`), apply the tag's old and new patch to the old version to get upstream's source change, apply that change to the tree our patch produces, and replace only the touched file sections of our patch with `git diff` sections of the new tree. Regenerating a whole patch doesn't reproduce ours (header comments, generated `md4c.js` sections). Check the result with `npx patch-package` on an unpacked copy: it must produce the intended tree.
   - Code: keep what both sides mean; when the commit comes from a branch, make the same resolution there. Abort and leave `local` as it was only when one side's intent is unclear or the checks fail and you can't fix them.
5. Update "Base", the table, and the check command in this file, and amend it into the `docs(fork)` commit (`git commit --fixup` and `git rebase -i --autosquash <new tag>`).
6. Run the check above. When a conflict was resolved in code, also install everything (`npm ci --ignore-scripts`), run `npm run typecheck`, and run the tests next to the files you changed.
7. Force-push `local` and every branch you changed.

To change one of our commits, change its branch, then cherry-pick the new commit into `local` in place of the old one. Branches of our own stay on upstream `main`, so they can become pull requests. To update an upstream pull request, fetch its head (`git fetch origin pull/<n>/head`) and replace the squash with a new one: `git diff $(git merge-base origin/main FETCH_HEAD) FETCH_HEAD | git apply --3way`. A pull request of someone else that needed real conflict work lives as a branch `pr/<n>-<topic>` on the fork instead: one squash commit authored by the PR's author, on the tag `local` is based on, since we can't push to the PR anyway. Move that branch to each new base tag along with `local` (its commit in `local`, minus what the commits below it changed), and redo the squash when the PR head moves past the commit named in the table. Drop a squash when upstream merges the pull request and the new base tag includes it.
